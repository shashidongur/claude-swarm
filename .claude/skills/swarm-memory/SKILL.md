name: swarm-memory
description: Read, write, and compact the swarm's per-project memory. Use to load what is known about a project at the start of any work on it, and to record what was learned — by a human directly, or by the retro role as a pull request.
allowed-tools: Read, Write, Edit, Grep, Glob, Bash

A cloud run keeps no state between runs. Memory is git, or it does not exist.

## Location

    memory/github.com/<owner>/<repo>/
      MEMORY.md              ≤ 40 lines: pointers to the indexes below + the top conventions/preferences/decisions   (curated)
      conventions.md         how this project works — commands, layout, naming, the swarm's own config mirror     (curated)
      preferences.md         how the owner wants work done here                                                  (curated)
      decisions.md           choices made, and why                                                                (curated)
      agents/<specialist>.md this project's own specialist roles, layered on the portable `dev`                   (curated)
      gotchas/INDEX.md       one line per gotcha; regenerated by lib/sh/memory-index.sh
      gotchas/*.md           curated gotchas (promoted by the owner)
      gotchas/auto/*.md      machine-written gotchas (retro); loaded fenced until promoted
      adrs/INDEX.md          "- [#7 live-session capacity](adrs/0007-live-session-capacity.md) — <decision> (merged <sha>)"
      adrs/<NNNN>-<slug>.md  10–20 lines: context, decision, consequences, pointer to <artifacts_dir>/<N>/adr.md at the merge sha
      postmortems/INDEX.md
      postmortems/<N>.md     one per merged issue (machine-written; fenced)
      runs/<N>.json          final dispatches[] + totals — machine-readable history for retro metrics and triage sizing
    memory/_swarm-itself/    the swarm's own lessons: probe results, token facts, design decisions

**Curated vs machine-written is the load-bearing split.** Curated files are read
unfenced by every brief. `gotchas/auto/`, `postmortems/` and `runs/` are read inside
`<untrusted source="swarm-written memory">` fences — a retro is a language model reading
attacker-influenced text, and a one-issue injection must not become a permanent unfenced
instruction for every later run. Promotion (a move from `gotchas/auto/` to `gotchas/`)
is the owner's act, in a memory PR.

## Format

One fact per file. Frontmatter, then the fact:

```markdown
---
name: <short-kebab-case-slug>
description: <one line, used to judge relevance>
metadata:
  type: preference | convention | gotcha | decision | reference | adr | postmortem
---

<the fact. For a preference or a gotcha, follow with **Why:** and **How to apply:**.
Link related memories with [[their-name]].>
```

Index files carry one line per entry: `- [Title](path.md) — hook`. `MEMORY.md` points
at the indexes rather than listing every gotcha itself — that is what keeps it under
forty lines on a project with dozens of them.

## Reading

Which files a role gets is data: `pipeline.yml roles[].memory` lists them per role
(`conventions.md` for almost everyone, `decisions.md` for triage/analyst/architect/
compliance, `gotchas/INDEX.md` for the builders, `adrs/INDEX.md` for the architect,
`MEMORY.md` + both indexes for retro). Each file is truncated at 8 KB with a note. A
human reading by hand does the same thing: `MEMORY.md`, then the files whose
descriptions bear on the work. Not all of them — a role that loads everything learns
nothing.

**Verify before you rely.** A note naming a file, a function, or a flag is checked
against the current tree before you act on it. Memory records what was true when it was
written. A stale note is corrected in the same run that found it wrong — by a human
directly, by the retro role in its "Proposed for curated memory" section.

## Writing

### By the retro role — a pull request, never a commit

At the end of every merged issue the `retro` role proposes `memory[]` in its
`result.json`: `postmortems/<N>.md` (required), `adrs/<NNNN>-<slug>.md` when the
architect wrote an ADR, and up to three gotchas under `gotchas/auto/`. Any role may
propose a gotcha along the way; retro sees the proposals and decides. The validator
(V13) refuses a path that already exists (except the issue's own post-mortem and run
record), a symlink, an append to a curated file, a `<!--`, an `@handle`, and any shell
command line outside a fenced block carrying `# verified against <path:line>`.

`advance` — the only job that holds `SWARM_TOKEN` besides `resolve`, and never one with
a model step — applies the entries into a fresh checkout of this repository, writes
`runs/<N>.json`, regenerates the INDEX files, checks `MEMORY.md ≤ 40` lines, commits as
`memory(<owner>/<repo>): #<N> retro`, force-pushes the branch
`memory/<owner>-<repo>/<N>` (it is ours; a re-run replaces it) and opens — or edits —
**one pull request** against the swarm branch. The owner's merge is the human gate on
memory: nothing lands on the branch the dispatcher executes from without a human
reading it. In the PR the owner may promote an auto gotcha or an ADR pointer to a
curated path (a move), edit it, or drop it.

When the push or the PR is refused (a `SWARM_TOKEN` without the write scopes), the
patch is uploaded as the artifact `swarm-<N>-memory-patch` (30 days) and the retro
comment says "memory not written (reason); patch attached — apply with `git am`".

### By a human — directly

Write a note when:

- the owner corrected you, and the correction generalises — that is a **preference**
- you lost time to something non-obvious about this codebase — that is a **gotcha**
- a question was settled that would otherwise be reopened — that is a **decision**
- you learned how this project actually runs its checks — that is a **convention**

Before writing, search for an existing note that covers the same ground and update it
rather than creating a second one; the indexes are the dedupe list. Do not write what
the repository already records — code structure, git history, the project's own
instructions file are read directly; record the *pointer*, not the content. Regenerate
the indexes (`lib/sh/memory-index.sh <owner/repo>`) and keep `MEMORY.md` under forty
lines.

## Compacting

Memory that only grows becomes noise. On a schedule:

- merge near-duplicate notes into the older file, keeping its name
- delete notes the code now contradicts
- promote `gotchas/auto/` entries that proved right; delete the ones that did not
- keep `MEMORY.md` under forty lines per project; past that, something needs merging

## Committing

A human commits `memory/**` on a branch and opens a pull request like any other change
— the executable branch is protected from runtime writes, and the same rule keeps hand
edits reviewable. Commit message:

    memory(<owner>/<repo>): <what was learned, in one line>
